# AGENTS.md — Our Places (Villa Booking Platform)

## 1. Project Overview & Role
**Our Places** is a high-performance, full-stack short-term property rental platform for luxury villas and apartments owned by me and my partners. The MVP is focused on 5 properties in Jamaica.

The application is structured as an **Isomorphic Rust Monorepo** targeting **GCP Cloud Run scale-to-zero** workloads. Core domain logic, pricing mathematics, and data models are shared seamlessly between backend services (Actix-web) and the WebAssembly frontend (Leptos).

---

## 2. Monorepo Crate Architecture

```
/our_places_rs
├── common/             # Isomorphic domain models, pricing math (rust_decimal), static reference data
├── db_core/            # PostgreSQL schema, SQLx entities, connection pooling, and migrations
├── app_api/            # Backend Microservices (Actix-web)
│   ├── listing_api/    # Property creation, search, geocoding (OSM/Nominatim), GCS signed URLs
│   ├── booking_api/    # Booking state machine, availability locking, payment orchestration
│   ├── user_api/       # JWT authentication, host profiles, shadow user promotion
│   └── image_worker/   # Pub/Sub background worker for image processing
├── web_app/            # Public-facing Leptos WASM frontend application
├── web_app_admin/      # Internal admin dashboard (listings, users, exchange rates)
├── web_app_common/     # Shared Leptos UI components (VillaCard, image components) & API client logic
├── infra/              # Terraform / Pulumi GCP infrastructure definitions
└── scripts/            # Deployment and operational scripts
```

### Monorepo Hard Rules
- **Shared Types**: All shared DTOs, domain models, and utilities live in `common` or `db_core`.
- **Dependency Flow**: API services and frontends depend on shared crates (`common`, `db_core`), **never on each other**.
- **No Circular Dependencies**: Sibling crates must not have circular cross-dependencies.

## 4. Key Domain Rules & Constraints

### Financial Precision ("Tri-Currency" Logic)
- **NEVER use floating-point types (`f32`, `f64`) for money, rates, or taxes**. Always use `rust_decimal::Decimal`.
- **Tri-Currency Flow**: Base Currency (villa price) $\rightarrow$ Payment Currency (user checkout currency) $\rightarrow$ Tax & Totals computation.
- **Static Tax Rates**: Statutory taxes (e.g. Jamaican GCT 15%) are stored statically in `common/src/reference.rs`. Volatile rates (Exchange Rates) live in DB tables.

### Booking Engine & Concurrency
- **Zero Double-Bookings**: Availability locking relies on PostgreSQL row-level locks (`SELECT ... FOR UPDATE`), not volatile caches.
- **Reservation Holds**: Initiating checkout creates a `pending_payment` record with a 15-minute `expires_at` window.
- **Audit Logging**: Every status transition (`pending_payment` $\rightarrow$ `confirmed` $\rightarrow$ `completed` / `refunded`) is logged immutably in `booking_status_history`.

### Image Pipeline
- Clients upload directly to Google Cloud Storage (GCS) via V4 Signed URLs generated by `listing_api`.
- Upload events trigger GCP Pub/Sub to wake up `image_worker` for WebP resizing (Mobile 640px, Tablet 1024px, Desktop 1920px).
- Frontend uses responsive HTML `<picture>` and `srcset` tags for optimal delivery.

## 5. Error Handling & Response Contracts

- **Domain vs. Application Errors**: Use `thiserror` for crate/library error enums and map them to unified application errors (`AppError`) in Actix-web handlers.
- **Consistent HTTP Payloads**: Errors return structured JSON payloads with explicit error codes (e.g., `{ "code": "DATE_UNAVAILABLE", "message": "The requested dates are no longer available." }`).
- **No Swallowed Errors**: Log errors using `tracing::error!` or `tracing::warn!` before returning user-facing API responses.

---

## 6. Database & SQLx Guidelines

- **Compile-Time Safety**: All SQL queries use `sqlx::query!` or `sqlx::query_as!` for compile-time schema verification against PostgreSQL.
- **Offline Query Metadata**: When modifying queries in CI/offline environments, ensure `cargo sqlx prepare` is updated if `sqlx-data.json` is enabled.
- **Immutable Migrations**: Never modify existing migration scripts in `db_core/migrations/` . Only create a new migration when the last migration is applied in the previous parent code branch - this is in an effort to reduce the number of migrations over time. Always create a new timestamped migration using `sqlx migrate add <migration_name>`.
- **Strict Type Mapping**:
  - Primary / Foreign Keys: `uuid::Uuid`
  - Timestamps: `chrono::DateTime<Utc>` (`TIMESTAMPTZ`)
  - Monetary / Tax Rates: `rust_decimal::Decimal` (`NUMERIC`)
  - Dynamic Attributes: `serde_json::Value` or typed Serde structs (`JSONB`)

---

## 7. Authentication & Shadow User Context

- **JWT Authentication**: Auth endpoints issue signed JWTs validated via `jsonwebtoken`.
- **Actix Auth Extractors**: Route handlers extract user identity via custom Actix extractors or `web::ReqData<Claims>`.
- **Shadow User Promotion**: Guest checkouts create a temporary "shadow user" tied to the 15-minute `pending_payment` hold. Post-payment, guests are promoted to full users without invalidating date holds.

---

## 8. Testing Strategy & Isolation Rules

- **Pure Unit Tests**: Unit tests for pricing logic, tax calculations, and domain validators live in `common/src/` and run without database dependencies (`cargo test -p common`).
- **Database Integration Tests**: API & database tests require a local PostgreSQL instance (`docker compose up -d`) and utilize isolated test transactions.
- **WASM Component Tests**: Frontend component logic in `web_app_common` is tested independently from backend HTTP servers.

---

## 9. Async & Concurrency Pitfalls ("Never Do" List)

- **NEVER use `f32` or `f64` for money, rates, or taxes**. Always use `rust_decimal::Decimal`.
- **NEVER run CPU-intensive or blocking synchronous I/O** directly on Tokio async worker threads. Use `tokio::task::spawn_blocking`.
- **NEVER stream raw image upload bytes through Actix HTTP endpoints**. Always issue GCP V4 Signed URLs for direct client-to-GCS uploads.
- **NEVER call `.unwrap()` or `.expect()` in production code paths or HTTP handlers**. Always use `Result<T, E>` error propagation.
- **NEVER bypass row-level database locking (`SELECT ... FOR UPDATE`)** when evaluating date holds or reservation availability.

---

## 10. Environment & Required Secrets

Ensure the following keys are present in `.env`:
- `DATABASE_URL`: PostgreSQL connection URI (`postgres://postgres:postgres@localhost:5432/our_places`)
- `JWT_SECRET`: Secret key for JWT signing and verification
- `GCS_BUCKET_NAME`: Target Google Cloud Storage bucket for villa assets
- `PUBSUB_TOPIC_ID`: GCP Pub/Sub topic for image worker events
- `EXCHANGE_RATE_API_KEY`: API key for currency exchange rate synchronization

---

## 11. Coding Standards & Performance Budgets

- **Cold Start Target**: $< 300\text{ms}$ (p50), $< 1\text{s}$ (p95) on Cloud Run ($0.25\text{ vCPU}$, $256\text{MB RAM}$).
- **No Panics**: Never call `.unwrap()` or `.expect()` in production/HTTP handler code paths. Always use `Result<T, E>`.
- **Structured Tracing**: Use `tracing` and annotate async handlers/functions with `#[instrument]`.
- **Standard Types**: Use `uuid::Uuid` for all entity IDs and `chrono::DateTime<Utc>` for timestamps.
